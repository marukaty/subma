# ADR-0007: CSV 取り込みジョブの冪等性と再実行

- **ステータス**: 採択
- **日付**: 2026-10-11（2026-10-12 追記: 再取り込みの重複）
- **決定者**: Marin Miyazaki
- **関連 ADR**: ADR-0003（CSV パイプラインの非同期実行）、ADR-0005（CSV PII 保護）

## 背景（Context）

本番の CSV 取り込みは、Cloud Tasks が `/internal/jobs/process_csv` に HTTP push し、Cloud Run のリクエストの中で `ProcessCsvJob` を同期実行する（ADR-0003）。この構成には次の問題があった。

- **Cloud Tasks は at-least-once 配信**: 同じタスクが複数回届くことがある。ジョブは状態を確認せずに `processing` で上書きしていたため、再送のたびに最初から処理し直していた
- **タイムアウトの不整合**: Cloud Run の `timeout` が 60 秒だった。AI 判定（Tier 3）を含むと 60 秒を超えることがあり、504 → Cloud Tasks の再送 → AI の再呼び出し（API 利用料が二重にかかる）、transactions の重複、完了済みの import が `failed` に上書きされる、が起きうる。また Cloud Tasks の HTTP タスクは `dispatch_deadline` の既定が 10 分で、Cloud Run 側を延ばしても Cloud Tasks 側が先に諦めて再送する
- **失敗後に再処理できない**: `ensure` で無条件にアップロードファイルを削除していたため、失敗した後の再送や再処理は必ず「no file attached」で失敗した
- **同時実行の上限がない**: 同じユーザーが続けてアップロードすると、複数の取り込みが並行して AI を呼び、Puma の少ないスレッド（3）を占有する

## 検討した選択肢（Options Considered）

### 選択肢 A: 状態遷移で処理権を取る（行ロック + status ガード）
- メリット: 既存の `csv_imports.status` をそのまま使える。DB のロックだけで完結し、追加の基盤が要らない。処理済み・処理中のものに再送が来ても、何もせず 200 を返して再送を止められる
- デメリット: 処理中にインスタンスが止まると `processing` のまま残る。止まったものを見分ける仕組み（経過時間による判定）と手動の再処理が必要

### 選択肢 B: Cloud Tasks のタスク名で重複を防ぐ（名前付きタスク）
- メリット: 同じ import のタスクを二重に登録できなくなる
- デメリット: 防げるのは登録の重複だけで、1 つのタスクの再送（タイムアウト後の再試行）は防げない。名前は削除後もしばらく再利用できず、再処理のたびに別名が要る

### 選択肢 C: 処理を小さな単位に分けて、単位ごとに冪等にする
- メリット: 1 リクエストを短くでき、タイムアウトに強い
- デメリット: 途中状態の保存や集約が必要になり、実装が大きくなる。現在の CSV の規模（月次明細、数百行）では過剰

## 決定（Decision）

**選択肢 A** を採用する。あわせてタイムアウトをそろえ、1 ユーザーの同時実行を 1 件にする。

### 状態遷移

```
                 dispatch（同じユーザーが処理中なら見送り、uploading のまま待つ）
                   │
  [uploading] ──── ProcessCsvJob が処理権を取る（ユーザー行と import 行をロック）
       ▲                 │
       │                 ▼
       │           [processing] → [rule_matching] → [ai_analyzing]
       │                                                │
       │                         ┌──────────────────────┴───────────┐
       │                         ▼                                  ▼
       │                   [completed]                          [failed]
       │                   ファイル削除                     ファイルは残す
       │                   次の待ちを登録                  error_summary を保存
       │                                                   次の待ちを登録
       │                                                          │
       └──────── 再処理（画面の「再実行」/ rake）◀──────────────────┘
                 ※ 処理中のまま 30 分以上止まったものも対象
```

- 処理権を取れるのは `uploading` のときだけ。`processing` / `rule_matching` / `ai_analyzing` / `completed` / `failed` のときは何もせず正常終了し、ログに `skipped: already <status>` を出す。Cloud Tasks には 200 を返すので再送されない
- 同じユーザーの別の import が処理中のときも処理権を取らず（`deferred`）、uploading のまま残す。処理中の import が終わったとき、ジョブが古い順に 1 件を登録する。登録時（dispatcher）と処理権の取得時（ジョブ）の両方で確認し、ジョブ側はユーザー行のロックで同時に 2 件が始まらないようにする
- transactions は import 単位で作り直す。保存の直前に、その import の transactions を消してから作る。削除・作成・`completed` への更新は 1 つの DB トランザクションで行う
- 失敗したときは `failed` にし、例外のクラス名だけを `error_summary` に保存する（メッセージには CSV の中身が混ざることがあるため保存しない）。例外はジョブの外に出さず 200 を返す。`failed` は再処理の操作でだけ `uploading` に戻す
- アップロードファイルは `completed` になったときだけ削除する（ADR-0005 の「完了/失敗後に即削除」のうち、失敗時を変更）。失敗時に残ったファイルは保存先バケットのライフサイクル（1 日）で消える
- 処理中のまま 30 分（Cloud Run のタイムアウトの 2 倍）以上更新がない import は「止まった」とみなす。同時実行の判定から外し、再処理の対象にし、画面の自動リロードを止める

### タイムアウトと再送

| 設定 | 変更前 | 変更後 | 根拠 |
|---|---|---|---|
| Cloud Run `timeout` | 60s | 900s | AI 判定まで 1 リクエストで終わる長さ。Cloud Tasks の HTTP タスクの上限（30 分）の範囲内 |
| タスクの `dispatch_deadline` | 未指定（既定 10 分） | 900 秒 | Cloud Run の timeout と同じにして、片方だけが先に諦めないようにする |
| Cloud Run `max_instance_request_concurrency` | 未指定（既定 80） | 3 | Puma のスレッド数と同じ。長い取り込みでスレッドが埋まったら別インスタンスに振り分けさせる |
| Cloud Tasks `max_concurrent_dispatches` | 5 | 2 | 取り込みが Web のリクエストを処理するスレッドを使い切らないようにする |
| Cloud Tasks の再送 | 最大 3 回、10〜300 秒の指数バックオフ | 変更なし | 再送は配送の失敗（インスタンス停止・5xx）向け。同じ import への再送は状態ガードで何もしないので、回数を増やす必要はない |

### 再取り込みの重複（2026-10-12 追記）

上の冪等性は「同じ import の再実行」を防ぐもので、同じ CSV を別の import としてもう一度アップロードすると、同じ取引が transactions に 2 件保存されていた。Tier 2 のパターン判定は過去の取引を使うため、重複は判定の材料も汚す。

- **同じ取引の定義**: 同じユーザーの（取引日, 利用店名, 金額）が完全に一致するもの（`Transaction.dedup_key`）。利用店名は CSV の値そのもの（前後の空白を除いたもの）、金額は数値として比べる
- **他の import 由来の同じ取引はスキップ**: 判定（Tier 1〜3）の前に、他の import で保存済みの同じ取引を除く。既存のレコードはそのまま残し、`csv_import_id` も付け替えない（最初の取り込みに紐づけたまま）。除いた件数は `csv_imports.skipped_duplicate_count` に保存し、画面に「既に取り込み済みの取引 N 件はスキップ」と出す。判定の前に除くので、重複分の AI 呼び出しも発生しない
- **同じ CSV 内の同じ取引は残す**: 同じ日に同じ店で同じ金額を 2 回払うことは実際にある。件数で突き合わせ、他の import で保存済みの件数を超えた分だけ保存する（例: 1 回目の CSV に 2 件、2 回目の CSV に 3 件 → 2 回目は 1 件だけ保存）
- **同じ import の再実行**: 自分の import の取引は数えない。これまでどおり、保存の直前に自分の取引を消してから作り直す
- **DB の一意制約（ユニークインデックス）は付けない**: 同じ日・同じ店・同じ金額の正当な複数件を DB が弾いてしまうため。CSV には取引を一意に識別する番号（承認番号など）が無く、制約に使える列が無い。重複の判定はアプリ側（ジョブ）で行い、1 ユーザーの処理を同時に 1 件に限る仕組み（上記）で、判定と保存の間に同じユーザーの取引が他から増えないようにする
- **既存データの掃除**: この変更より前に二重に保存された取引は、`bin/rails 'transactions:dedup[USER_ID]'` で消す。取り込みの古い順に見て、それまでの取り込みで保存済みの件数を超えた分だけを残す（ジョブと同じ判定）。`[USER_ID,dry_run]` または `DRY_RUN=1` で、削除せずに候補だけを表示する。消した分は、その取り込みの `skipped_duplicate_count` に加え、`matched_count` を数え直す

あわせて `csv_imports.matched_count`（画面の「サブスク判定」）を、サブスクと判定された取引（`classification = subscription`）の件数に限定した。これまでは AI が「サブスクではない」と判定した行も数えており、レビュー一覧の件数と一致しなかった。既存の import はマイグレーションで数え直す。

### 再処理の手段

- 利用者本人: 取り込み詳細画面の「再実行」ボタン（`POST /csv_imports/:csv_import_id/retry`。本人の import のみ、CSRF トークンあり）
- 運用者: `bin/rails 'csv_imports:retry[ID]'`
- どちらも `failed`（または止まった処理中）のときだけ受け付け、ファイルが残っていなければ再アップロードを案内する

## 結果（Consequences）

### ポジティブ
- 同じタスクが何度届いても、AI の呼び出しと transactions の作成は 1 回だけになる
- 失敗した取り込みを、ファイルを上げ直さずに再処理できる
- 1 ユーザーが同時に使う Puma のスレッドと AI の呼び出しが 1 件分に限られる

### ネガティブ・トレードオフ
- 処理中にインスタンスが止まると、30 分たつまで同じユーザーの次の取り込みが待たされる
- 失敗時はファイルがバケットのライフサイクル（最大 1 日）まで残る。PII を含むファイルが残る時間は延びるが、アクセスできるのは Cloud Run の SA だけで、期限で必ず消える
- `failed` は自動では再試行しない。一時的な障害（API の一時停止など）でも、利用者か運用者の再実行が必要

### フォローアップ作業
- `terraform apply`（Cloud Run の timeout・同時リクエスト数、Cloud Tasks の同時実行数）
- ADR-0005 の「失敗後即削除」の記述を、本 ADR に合わせて更新する（別 PR）
- 処理行数・AI 判定量の上限（コスト上限）は別途対応する
- 既に二重に保存されている取引の掃除（`transactions:dedup`）を本番で手動実行する
