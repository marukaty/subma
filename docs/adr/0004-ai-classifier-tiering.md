# ADR-0004: サブスク抽出の階層化分類器（Tier 1 / 2 / 3）

- **ステータス**: 採択
- **日付**: 2026-04-28
- **決定者**: Marin Miyazaki
- **関連 ADR**: ADR-0003（CSV パイプライン）、ADR-0005（CSV PII 保護）、ADR-0006（ログイン許可リスト）、ADR-0007（CSV ジョブの冪等化）、ADR-0008（通信費の除外・店名の正規化）

## 背景

CSV 取り込みからサブスクを自動抽出するうえで、以下を同時に成立させる必要があった:

1. **精度** — 既知サービス（Netflix 等）は確実に拾い、未知サービスも適切に推定する
2. **コスト** — Claude API は呼ぶたびに数円〜数十円かかる。無差別に全行を AI に投げると月予算をすぐ超える
3. **速度** — 数百行の CSV を数秒で処理してユーザーを待たせない
4. **プライバシー** — クレジットカード明細という PII を最小限の外部送信に留める（NFR-S-10）

要件定義書 §5 で「Tier 1 規則ベース → Tier 2 パターン検出 → Tier 3 Claude API」の階層化が指定されている。本 ADR はこの階層構造を採択する判断と各段の責務を確定させる。

## 検討した選択肢

### A. すべて AI に丸投げ（Tier 3 のみ）
- メリット: 実装がシンプル
- デメリット:
  - 50 行 CSV ＝ 1 リクエストでも、毎月複数ユーザー × 複数 CSV で API コストが嵩む
  - "NETFLIX.COM" のような確定的にわかる行も AI に投げてしまうのは無駄
  - レイテンシが API 応答に常に縛られる

### B. すべて規則ベース（Tier 1 のみ）
- メリット: 速い、無料、決定的
- デメリット:
  - ServiceTemplate にない未知サービスを取りこぼす
  - パターンは保守し続けないと陳腐化する
  - 差別化の核（AI 抽出）が無くなる

### C. 階層化（Tier 1 → Tier 2 → Tier 3）— 採択
- メリット:
  - 確定できる行を高速・無料で消化（Tier 1 で 6〜8 割を見込む）
  - 規則に無いが繰返しパターンがあるものを履歴照合で拾う（Tier 2）
  - 残りだけ AI に投げる → API コストとレイテンシを最小化
- デメリット:
  - 実装ファイル数が増える（3 つの分類器 + パイプライン統合）
  - 各段の責務とフォールバック挙動を明文化しないと混乱する

## 決定

**C を採択し、各 Tier の責務を以下に固定する。**

### Tier 1: `Classifiers::RuleClassifier`
- ServiceTemplate.match_patterns（正規表現の配列）に対して description をマッチ
- ヒット → confidence 1.0 で確定、subscription として `classified` バケットへ
- ヒットしない → そのまま `unclassified` を返し、Tier 2 へ流す
- 計算量: O(rows × templates)、ServiceTemplate は起動時にメモリキャッシュ
- 照合前に description とパターンの両方を Unicode NFKC で正規化する（半角カナ・全角英数の店名対応。ADR-0008）
- 通信費（携帯・回線・プロバイダの月額）はテンプレートを置かず、サブスクの対象外とする（ADR-0008）

### Tier 2: `Classifiers::PatternClassifier`
- 入力: Tier 1 で `unclassified` だった行
- 同じ description + 同じ amount の取引について、**取引日の間隔が「月額相当」または「年額相当」になるペアを 1 組以上**作れたらサブスク候補
  - 月額相当: 25〜35 日（`MONTHLY_INTERVAL_RANGE`）
  - 年額相当: 360〜370 日（`YEARLY_INTERVAL_RANGE`）
  - ペアの相手は (a) ユーザーの過去 transactions、(b) 今回取り込み中の rows 同士 のどちらか
  - 履歴を遡る期間: 月額相当は直近 N ヶ月（既定 6）、年額相当は直近 13 ヶ月。履歴は description・amount で絞ってから日付だけを取得する
- ヒット → confidence 0.7 で `classified`、はずれ → `unclassified` を返し Tier 3 へ
- ユーザー単位で過去履歴を見る（テナント分離）
- 店名の比較は完全一致。履歴側の description は正規化前の文字列で保存されているため、
  NFKC 正規化＋大文字小文字無視での比較は、保存時の正規化と合わせて別途対応する

#### 改訂（2026-10）: 「件数」から「取引日の間隔」へ

当初は「直近 3 ヶ月に同 description + 同 amount が 2 件以上」で判定していたが、本番運用で次の誤判定が見つかった。

- 同じ CSV を 2 回取り込むと、1 回目で保存された取引が 2 回目の判定で履歴として数えられ、取り込み中の行が自分自身にマッチする
- 同じ月に別々の利用で偶然同額になった 2 件（例: 通行料金のような都度課金）が、「2 件以上」を満たしてサブスク候補になる

「異なる年月に 2 回以上」という数え方も検討したが、9/30 と 10/2 のように月をまたぐ数日差の同額を繰り返しとみなしてしまう。
サブスクは一定の周期で同額が請求されるものなので、**取引日の間隔そのもの**で判定することにした。

- 同じ日付同士（自分自身や、再取り込みで重複した履歴）は間隔 0 日なのでペアにならず、再取り込みでの自己マッチが起きない
- 同月内や月をまたぐ数日差の偶然の同額はペアにならない
- 月額は請求日のずれ（月の日数の違い・営業日による前後）を見込んで 25〜35 日、年額は 360〜370 日とした
- 年額のペアを見つけるため、履歴を遡る期間は年額相当だけ 13 ヶ月に広げた
- 1 ファイルに複数月分が含まれる場合に初回取り込みでも拾えるよう、取り込み中の rows 同士の照合も行う
- 隔月・3 ヶ月ごとなどの周期は今回は対象外。間隔の範囲を定数（`INTERVAL_RULES`）に追加すれば拡張できる

なお、同じファイルの再取り込みで取引が重複登録される問題自体は、パイプライン側（`ProcessCsvJob`）の変更として別途対応する。

### Tier 3: `Classifiers::AiClassifier`
- 入力: Tier 1/2 でも判定できなかった行
- Anthropic Claude API（`claude-sonnet-4-6`）にバッチ 50 件 / req で投げる
- 出力: subscription / non_subscription それぞれに classifier "ai" + confidence + 推定サービス名・カテゴリ
- API 失敗（レート制限・JSON パース失敗・タイムアウト）→ 該当バッチ全体を `unclassified` として返し unknown 扱い
- **PII マスキング（NFR-S-10）**: 連続 4 桁以上の数字を `XXXX` に置換、user_id/email は payload に含めない
- **プロンプトキャッシュ**: system プロンプトに `cache_control: ephemeral` を付与、同一ユーザーの連続インポートでコスト削減
- **指数バックオフリトライ**: レート制限・サーバー過負荷で最大 3 回リトライ

### 利用量の上限（2026-10 追記）

Tier 3 は呼ぶたびに課金されるため、悪意のある大きな CSV の繰り返しや操作ミスで費用が膨らむ（コスト攻撃）。
これを防ぐため、AI に送る行数に上限を設けた。値はすべて環境変数で変更でき、既定値をコードに持つ。

| 上限 | 既定値 | 環境変数 | 実装 |
|---|---|---|---|
| CSV 1 回の取引の行数（ヘッダを除く） | 1,000 行 | `CSV_MAX_ROWS` | `CsvUploadForm`（超えたら 422）。ジョブ側でも確認する |
| AI に送る行数（取り込み 1 回） | 300 行 | `AI_MAX_ROWS_PER_IMPORT` | `AiUsageLimiter` |
| AI に送る行数（1 ユーザー 1 日） | 500 行 | `AI_MAX_ROWS_PER_USER_PER_DAY` | `AiUsageLimiter`（`ai_usage_counters`） |
| AI に送る行数（全体 1 日） | 2,000 行 | `AI_MAX_ROWS_PER_DAY` | `AiUsageLimiter`（`ai_usage_counters`） |

#### 超えたときの挙動
- 上限を超えた分は AI に送らず、unknown（未判定）として保存する。取り込み自体は completed にする
  （API 障害時と同じく、機能を落として処理を続ける。ユーザーはレビュー画面で手動で登録できる）
- 送らなかった行数を `csv_imports.ai_skipped_count` に残し、画面に「AI 判定の上限に達したため N 行は未判定」と出す
- どの行を送るかは CSV の上からの順。AI の上限を 0 にすると AI を使わない（緊急停止）

#### 日次の数え方
- `ai_usage_counters` に「ユーザー × 日」と「全体 × 日」（user_id が NULL）の行を持ち、AI に送る前に
  今回送る行数を予約する。全体 → ユーザーの順に行ロックを取り、上限の確認と加算を同じトランザクションで行う
- Cloud Run はインスタンスが複数になりうるため、メモリやインスタンスごとの保存（Rack::Attack の保存先など）では数えない
- 日付はアプリのタイムゾーン（Asia/Tokyo）の 0 時で切り替わる
- 予約した行数は、API 呼び出しが失敗しても戻さない（課金された可能性があり、安全側に倒す）
- MySQL の一意インデックスは NULL を重複とみなさないため、`COALESCE(user_id, 0)` の生成列 `user_key` と日付で一意にする

#### 同じ取引をまとめて送る（重複除去）
同じ取り込みの中で「店名（正規化後）＋金額」が同じ行は、先頭の 1 行だけを AI に送り、結果を同じキーの全行に当てる。
上限の行数も、まとめた後の件数で数える。

- 店名は Tier 1 と同じ NFKC 正規化に加えて、大文字小文字の無視・空白の詰めをしてから比べる（ADR-0008）。
  PII マスク後の文字列で比べるので、カード番号などの数字だけが違う店名は 1 つにまとまる（AI に送る内容が同じため）
- **金額をキーに含め、店名だけではまとめない。** 理由:
  - このプロンプトは日付・店名・金額を渡してサブスクかどうかを判定させており、金額も判断材料になっている
  - 「AMAZON.CO.JP」「APPLE.COM/BILL」「GOOGLE」のような汎用の店名は、同じ店名に定額の会員費と単発の買い物が混ざる。
    店名だけでまとめると、600 円の会員費と 3,280 円の買い物に同じ判定（とサービス名）が付いてしまう
  - Tier 2 も「同じ店名＋同じ金額」を同じ取引の繰り返しとみなしており、考え方をそろえられる
- 日付はキーに含めない。毎月同じ金額で請求されるサブスクは、何か月分あっても 1 行にまとまる
- 店名だけでまとめる場合に比べ、金額が毎回違う店（スーパー・飲食店など）は行数が減らないが、そこは上限で抑える

#### 費用の見積もり（`claude-sonnet-4-6`: 入力 $3 / 出力 $15 per MTok）
- 1 行あたりのトークン: 入力（`{"id":..,"date":..,"description":..,"amount":..}`）が約 40〜60、
  出力（`{"id":..,"is_subscription":..,"confidence":..,"service_name":..,"category":..}`）が約 50〜60
- 1 リクエスト（50 行）: system プロンプト約 700＋取引 約 2,500〜3,000 で入力 約 3,500、出力 約 3,000
  → 入力 $0.011＋出力 $0.045 ≒ **$0.06／50 行（約 $0.0012／行）**
- 最悪の場合（出力が MAX_TOKENS 8,000 まで出る）: 入力 $0.011＋出力 $0.12 ≒ $0.13／50 行
- 上限での最大額（概算）:

| 単位 | 行数 | 通常 | 最悪 |
|---|---|---|---|
| 取り込み 1 回 | 300 行（6 リクエスト） | 約 $0.36 | 約 $0.78 |
| 1 ユーザー 1 日 | 500 行（10 リクエスト） | 約 $0.60 | 約 $1.3 |
| 全体 1 日 | 2,000 行（40 リクエスト） | 約 $2.4 | 約 $5.2 |
| 全体 1 か月（毎日上限まで） | 60,000 行 | 約 $72 | 約 $156 |

上限なし（以前）は 1 回の取り込みで約 3 万行（5MB）を送れたため、上限で 1 日の最大額を数ドルに抑えられる。
1 か月で上限まで使い切る状態は想定外のため、外側の安全網として Anthropic コンソールの月額上限（例: $30）と
GCP の予算アラートを設定する（手順は `docs/infrastructure-notes.md` 8.8）。

#### 既定値の根拠
- CSV 1,000 行: カード明細 1 か月分は多くても数百行。1MB のサイズ上限（約 2 万行入る）より先に、行数で止める
- 取り込み 1 回 300 行: Tier 1/2 で 7〜8 割が判定済みになる前提で、1,000 行の CSV でも AI に回るのは 200〜300 行程度。
  重複をまとめるとさらに減る
- 1 ユーザー 1 日 500 行: 通常の利用（月 1〜2 回の取り込み、数か月分のまとめ取り込み）では届かない値
- 全体 1 日 2,000 行: 招待制（ADR-0006）の利用者数で、通常の利用では届かない値。超えたら異常とみなして AI を止める
- 同時に処理する取り込みは 1 ユーザー 1 件（ADR-0007）。この上限と組み合わせて、並列のアップロードで上限をすり抜けられないようにしている

### パイプライン統合（`ProcessCsvJob`）
```
parse → Tier 1 → Tier 2 → Tier 3 → save_transactions → purge_csv_file (NFR-S-09)
```
ステータス遷移: `processing → rule_matching → ai_analyzing → completed`

ユーザーは抽出結果レビュー画面でチェック除外・サービス名/カテゴリ修正をしたうえで、選択した行を Subscription にまとめて変換する。

## 結果

### ポジティブ
- Tier 1 で多くの行を高速消化、API コストが Tier 3 に届く件数に比例（典型的に元の 2〜3 割程度）
- API 障害時もパイプライン全体は止まらず、unknown 扱いで保存・後でユーザーがレビュー可能
- 各分類器の責務が単一、ユニットテストしやすい
- 将来、Tier 4（カスタム ML モデル）を挟む余地もある

### ネガティブ・トレードオフ
- 実装ファイルが増えた（3 つの分類器 + ADR）
- Tier 1 の正規表現パターンを保守する手間（ServiceTemplate.match_patterns の更新）
- AI 出力の信頼度を最終的にユーザーが目視確認する設計のため、完全自動化はしていない

### フォローアップ
- ✅ 本番の非同期処理を Cloud Tasks に移行（ADR-0003 の追記）
- Anthropic Console での月予算アラート設定（手順は `docs/infrastructure-notes.md` 8.8。アプリ側の上限は「利用量の上限」節）
- 学習データ蓄積: ユーザーがレビュー時に AI 判定を修正したケースを匿名化保存して将来の Tier 1 パターン強化に活かす（v2 以降）
